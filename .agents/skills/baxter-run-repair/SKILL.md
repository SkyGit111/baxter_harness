# 修复 Baxter 运行故障

1. 找到用户所指的运行目录。读 `events.jsonl` 中的任务、手臂、后端、最后一个有完成证据的步骤和第一条失败事件。用 `obs_id` 关联观测和选点，用 `plan_id` 关联原语预检、执行与机器人侧审计。旧记录缺少的字段标为未知。
2. 按故障选择复现方式。

   - 视觉或选点问题，在包含初始观测和语义计划的历史运行上执行 `python scripts/compare_planner_views.py --run <运行目录> --output <新文件.json>`。从结果检查选图数量、腕图被省略的原因和观测编号。默认运行只生成离线清单。检查实际请求构造时再运行 `tests.test_api_stream` 和图像相关测试。
   - 运动中断问题，定位到具体阶段和第一条拒绝记录。例如遇到 `segment_tracking_rejected`，检查哪一关节、哪个轨迹段、当时的跟随误差。遇到闭爪后抬升被拒，分别检查起始接触、上升路径和抬升终点的约束。用失败情形与一条应当被拒的轨迹共同验证修复。
   - 耗时问题，从 `call-chain.json` 和 `timing-summary.json` 找最耗时的调用，再回到 `events.jsonl` 或机器侧审计核对。分别报告 API 首个文本增量、请求总耗时和机械阶段耗时。一次调用里的子阶段与父调用分行呈现，防止重复累计。

3. 修复实际入口使用的代码，运行能命中该故障的测试或回放，对照修复前的失败点。用户暂停真机任务时继续进行已要求的离线排查。电机是否执行过尚不确定时，恢复真机工作须先读取新状态和观测。
4. 交付时给出故障位置、改动入口、复现命令以及能查到结果的事件或文件。实测耗时写明运行与阶段。现场抓取或堆叠以执行回执和动作后的观测判断，分别注明离线与真机验证到了哪一步。
