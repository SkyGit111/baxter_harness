# 完整操作的 XYZ 可达性采样

`cix_harness.reachability` 使用保存的 URDF、双臂状态和现场配置，为左右臂分别检查“抓取、抬升、搬运、放置或堆叠、退开”的完整计划。它不创建机器人接口，不发布运动、夹爪或 ROS 服务请求。全部结果是**尚未真机认证的离线候选**。

扫描依据固定的起始关节姿态、另一臂的状态、夹指/TCP 模型和放置目标。它不把两端可达当成中间路径可达，也不将零散通过点的包围盒称为连续可达区域。改变机器人或相机位置后，旧外参和扫描结果需要重新核验。

## 输入与运行

在已经配置 ROS Noetic、PyKDL、`geometry_msgs`、`tf` 的控制主机中运行。模型与状态都来自文件；不需要连接机器人本体或启动 bridge。`--states` 接受保存的 `arm_states` 观察、`after_arm_states` 结果，或直接的左右臂状态映射。每个受测臂应从明确记录的空夹爪姿态开始，不能直接把实际持物状态修改为空载。

`grid.json` 示例：

```json
{
  "x": [0.45, 0.60, 0.75],
  "y": [-0.35, 0.00, 0.35],
  "z": [-0.16, -0.12, -0.08, -0.04]
}
```

所有坐标单位为米，使用 Baxter `base` 坐标系。这里的 z 是**目标物体顶面参考点的高度**；不是夹爪 TCP 高度，也不是抬升后的高度。扫描高于当前桌面的点时，意味着评估“如果该高度存在目标及支撑”的几何条件，不代表现场真的存在物体或支撑面。

`destinations.json` 示例：

```json
{
  "left": [0.60, 0.25, -0.16],
  "right": [0.60, -0.25, -0.16]
}
```

这是示例目标，不是现场标定值。每个值代表放置支撑面的顶点高度：放到桌面时使用当地桌面高度，堆叠时使用底部物体的顶面。必须替换为当前任务目标。完整操作区域会随放置位置变化。

```bash
source /opt/ros/noetic/setup.bash
source /home/cothink/catkin_ws/devel/setup.bash
# 可选：明确阻止此进程访问真实 ROS master，验证它只使用保存的数据。
export ROS_MASTER_URI=http://127.0.0.1:1
python3 -m cix_harness.reachability \
  --config site/dual-trial-preview.local.json \
  --states site/recorded-dual-state.json \
  --urdf site/robot-description.urdf \
  --grid site/grid.json \
  --destinations site/destinations.json \
  --yaw-degrees 0 90 180 270 \
  --placement-skill stack \
  --output runs/reachability/report.json
```

可用 `--arms right` 单独评估右臂。工具仅使用控制主机上的 Python 依赖；无需让天数 GPU 参与。Windows 上没有 PyKDL/ROS 时可以查看报告、运行核心单元测试，但不能声称已经完成真实模型扫描。

## 如何理解报告

- `arms.<arm>.samples` 保留每个 XYZ 样本及每个抓取 yaw 的结果。`candidate` 表示至少一组候选完成了整条计划的已实现检查；`no_candidate_found` 只表示这次有限搜索没有找到。
- `z_slices` 给出每层 z 的原始样本索引和通过数量；`sampled_candidate_z_values_m` 只列出有通过样本的离散高度，不填补其间空洞。
- `operations` 分开记录 pick 和 stack/place 的路径点数、头部/另一臂检查结果，以及该操作路径采样到的 TCP 高度极值。
- `failure_type`、`reason` 标明失败发生在哪个操作及是哪类约束。工作区配置拒绝、IK 无解、头部干涉需要分别分析；配置边界过小不等于真实机械极限。
- 指纹绑定 URDF、原始配置、实际评估配置和起始状态，防止移动机器人或改变几何后复用旧结果。

当前 evaluator 使用固定历史姿态作为连续 IK 初值，并枚举夹爪绕 base Z 的朝向；它尚不是覆盖所有肘部构型和绕障路径的全局规划器。头部球体与双臂包络检查默认启用，但躯干、同臂非相邻连杆、桌边和其他障碍物的完整 mesh 碰撞检查还不能由这份报告代替。夹取成功、物体是否滑动和原厂避让的实际干预也需要现场验证。

确认候选后，应依次验证抓取、抬升、搬运、放置和退开，再标记为该任务的现场通过点。左右臂联合操作还需要分别检查交接姿态及双方持物几何；两张单臂图的简单并集不能证明双臂任务可行。

### 使用保存的 MoveIt 场景复核全身路径

在控制主机的 Noetic 工作环境，把当前完整 MoveIt 场景、URDF、SRDF 和应用于现场的碰撞盒保存到一个新目录。先记录双臂起姿，保持双臂静止，随即读取场景。归档程序使用 `/get_planning_scene`，只把桌面、夹具等配置碰撞盒加入内存副本。现场照片、标定和归档文件放在项目的私有目录。

```bash
python3 -m cix_harness.reachability_scene --config site/dual-current.local.json \
  --output site/moveit-snapshot
g++ -std=c++14 -O2 scripts/offline_scene_check.cpp -o /tmp/baxter-offline-scene-check \
  $(pkg-config --cflags --libs moveit_core srdfdom urdf)
```

在上面的 XYZ 扫描命令中加入 `--moveit-snapshot site/moveit-snapshot --moveit-checker /tmp/baxter-offline-scene-check`，`--urdf` 使用同一次保存的 `site/moveit-snapshot/robot.urdf`。从这一阶段起，可把 `ROS_MASTER_URI` 设为 `http://127.0.0.1:1`。扫描会核对模型和现场配置摘要、两臂 14 个关节的起姿，对每个动作阶段调用与执行器相同的关节曲线采样，用 MoveIt/FCL 检查存档中的全身、台面和附件。报告中的 `archived_moveit` 和 `checked_curve_samples` 分别给出场景来源、逐阶段样本数。`approach_failures` 会同时保留直接接近和分阶段接近各自遇到的问题，便于定位失败的是 IK、桌面、头部还是另一只手的附件。

夹指开合和持物转换仍由原语在规划中模拟。FCL 使用存档时夹指的关节位置，持物底部和双臂净距沿用原语检查。未建模的桌面物体、抓取是否打滑以及指尖与实物的接触仍需现场记录验证。

## 搬动底座后怎样评估 MoveIt

### 用新测桌面生成左右臂现场候选配置

保存本次手眼标定和测量为两个 JSON 文件。所有坐标均以米为单位。下面的数字是**演示格式的合成数据**，现场请替换为本次测量。第一份文件 `site/extrinsics-new.json` 表示 `p_base = R × p_color_optical + t`，四元数顺序为 XYZW。

```json
{"source":"本次标定文件或测量记录编号","units":"m","from_frame":"camera_color_optical_frame","to_frame":"base","xyzw":[1,0,0,0],"translation_m":[0.5,0,1]}
```

第二份文件 `site/table-measurements-new.json` 中的桌角须按物理周界依次记录。支持顺时针和逆时针，末点无需重复起点。每组点分别写明所属的 `base` 或所选颜色光学坐标系。光学坐标是对齐彩色图后的 XYZ 深度反投影值。可选的 `check_points` 是单独测量的桌面点，它们用于检验桌面高度，不参与拟合。可选的 `reference_pairs` 用同一实体点的光学读数和独立 base 三维测量检验外参，能发现桌面内方向的平移误差；可在几个相隔较远的位置取点。

```json
{
  "source":"本次桌面测量记录编号",
  "units":"m",
  "boundary":{"frame":"camera_color_optical_frame","points_m":[[-0.2,-0.3,1.17],[0.2,-0.3,1.16],[0.2,0.3,1.16],[-0.2,0.3,1.17]]},
  "check_points":{"frame":"base","points_m":[[0.5,0,-0.165]]},
  "reference_pairs":[{"color_optical_m":[0,0,1.165],"measured_base_m":[0.5,0,-0.165]}]
}
```

下例的垂直高度误差 5 mm、配对点三维误差 8 mm 是示范参数，应按本次方块和夹爪余量选取。相机使用不同 ROS 名称时，可用 `--optical-frame` 显式指定实际颜色光学帧。

```bash
python3 -m cix_harness.table_survey --extrinsics site/extrinsics-new.json \
  --survey site/table-measurements-new.json --max-height-error-m 0.005 \
  --max-reference-error-m 0.008 --output site/table-geometry-new.json
python3 -m cix_harness.prepare_site --template config/baxter-primitives.example.json \
  --geometry site/table-geometry-new.json --output-dir site/new-layout
```

第一条命令输出实际边界、平面方程、拟合与独立检查的高度误差、外参配对误差和两个输入的哈希。第二条生成左右臂及双臂候选，校准和真机放行标记均为假。只有三个边界点时它们本身即可确定一个平面，此时独立测点尤其重要。

### 比较局部 IK 和到预抓位的绕行

搬动底座会改变相机、桌面和目标相对 `base` 的坐标。头部和关节之间的机械安装关系保持固定。先用新外参、桌面平面和双臂新起姿重跑上面的任务采样。若比赛中的左右臂目标都能从新布局完成整套动作，换肘姿和全局绕行的优先级可以降低。若同一任务反复在头旁转腕或转运时失败，就用同一目标比较局部 IK 和 MoveIt 的绕行结果。

本项目有两个只读评估入口。原始机器人模型可在普通 Python 上盘点。

```bash
python -m cix_harness.moveit_probe --urdf site/robot-description.urdf --output model-inventory.json
```

可加 `--srdf site/robot-description.srdf` 核对规划组和 SRDF 忽略的连杆对。11 月 17 日保存的 Baxter URDF 含有碰撞几何的 37 个连杆，共 27 个圆柱、5 个球、9 个盒。它覆盖躯干、头部避让球、底座及两手标称指节与指尖。现场需要对照长夹指的伸出长度、张开宽度、夹持方块后占用的空间，以及新桌面的位置和尺寸。

在配置了 Noetic、Baxter 机器人描述和 MoveIt `move_group` 的控制主机或仿真机上，可以评估原语的预抓移动。取新配置下预备阶段的 `tcp_m` 和 `xyzw`，下列大写变量代表这两组实测或规划值。工具按所选手臂的 TCP 偏移求出 `right_gripper` 的目标，左臂同理。使用已经换算好的 EEF 坐标时可直接传 `--eef-base-m`，省略 `--config`。

```bash
python3 -m cix_harness.moveit_probe --ros --arm right \
  --config site/dual-current.local.json --tcp-base-m "$X" "$Y" "$Z" \
  --eef-xyzw "$QX" "$QY" "$QZ" "$QW" --output right-pregrasp.json
```

工具读取 `/get_planning_scene`，把该快照中的双臂起姿提交给 `/check_state_validity`。如果起姿碰撞，报告记录可取得的连杆对。如起姿有效，就向 `/plan_kinematic_path` 请求所选臂从该姿态到预抓位的路径。规划组名称可用 `--group` 指定，规划器可用 `--planner-id` 指定。运行结果保留场景物体和形状、状态时间戳、模型指纹、允许碰撞矩阵、规划耗时、关节行程和预计轨迹时长。检查场景里的桌子是否与新标定对得上。报告中的时间是 MoveIt 在指定缩放下的预计值，真机执行仍以机器侧日志计时。这条入口只评估预抓移动，完整任务继续逐段检查下探、夹取、搬运、放置和退开。[MoveIt Noetic 规划场景文档](https://moveit.github.io/moveit_tutorials/doc/planning_scene/planning_scene_tutorial.html) · [ROS 1 规划服务实现](https://github.com/moveit/moveit/blob/noetic-devel/moveit_ros/move_group/src/default_capabilities/plan_service_capability.cpp)

对于此次头部绕行，优先评估控制主机的 MoveIt 1 规划组和采样规划器。PyRoKi 更适合在已知可行的初始轨迹附近批量优化姿态、关节行程和避障代价。它支持 JAX CPU，要求 Python 3.10 及以上，上游对网格使用胶囊近似，未内置采样式路径搜索。若后续评估 PyRoKi，需为 Baxter 长夹指和桌面建立与现场相符的几何，在独立 Python 环境分别记录首次 JIT 和复用后的耗时，再让同一套模型复检它的候选路径。[PyRoKi 上游说明](https://github.com/chungmin99/pyroki)
