# Baxter 与 TY1100 具身 Harness 项目完整交接

更新日期：2026 年 11 月 10 日。面向接手开发、部署和现场联调的同学。

本交接对应代码版本 `5ce8423`。此前现场部署并完成局部抓取的版本是 `4d5edf8`；新增恢复逻辑已提交仓库，但没有据此宣称现场进程已升级。文中的机器和服务状态是最近一次现场记录，重新进入实验室必须重新查询。

最重要的结论：我们已有可以部署、调用真实模型并驱动 Baxter 的项目初版，不再只是板卡测试包。π0.5 已成功加载和推理，两模型同卡运行也已验证；但 π0.5 对 Baxter 的动作适配尚未成立。另一条 VLM 加动作原语路线已经实现，且原语完成了一次人工定位后的真实抓取。完整视觉自主定位、自动恢复和堆叠还不能宣布成功。

## 1 项目目标与工程原则

比赛目标是让 Baxter 根据中文指令操作桌面物体，例如抓起指定颜色的小方块、搬运到指定位置、把一个方块叠到另一个上面。重点是现场效果、可重复执行、失败后能恢复，以及能够清楚解释自己的工程贡献。

这不是以论文为目标的研究项目。没有专门安排学术 baseline、消融实验或为探索而探索的工作。工程测试用于防止重复发动作、坐标错误、误报成功等实际问题；真机记录用于判断下一步修哪里，不等同于论文实验。

基本决策如下：

1. 优先全端侧模型推理：VLM 和 VLA 都放在天数板子上。Baxter 控制电脑仍负责 ROS、相机和电机接口；“端侧”不表示所有进程必须塞进一个操作系统。
2. 优先使用 π0.5，而不是将早期 Qwen2.5-VL-3B 与 OpenVLA 组合当作最终方案。
3. 复用可靠开源代码和已有 Baxter 项目，重点开发机器人适配、执行反馈、任务恢复与部署系统。
4. VLM 加 VLA、VLM 加动作原语两条路线现在并行推进。原语不再是只有前两种训练方案失败才考虑的远期兜底。
5. 模型能推理、机械臂能移动、能正确抓物是三个不同的验收层级。
6. 不以毫米级微动演示代替有效任务。动作幅度应由任务、可达性和现场空间决定；长距离垂直上移也可能因关节构型而不可达。

## 2 全部路线与决策条件

### 2.1 两条当前执行路线

| 路线 | 高层输出 | 低层执行 | 当前主要价值 | 尚未解决 |
| --- | --- | --- | --- | --- |
| VLM 加 VLA | 中文目标转换成短英文子任务 | π0.5 根据图像和本体状态预测动作，经适配后执行 | 保留学习策略完成接触操作的能力 | LIBERO 检查点与 Baxter 的状态、动作和视角差异 |
| VLM 加原语 | 白名单技能和图像中的二维目标点 | 深度定位、坐标变换、参数化轨迹、IK、电机 | 尽快获得可解释、可调试的桌面抓放系统 | 精确标定、完整视觉定位、恢复和堆叠真机验收 |

两个入口共用硬件与控制基础设施，但还没有一个能在同一任务中自动选择“这一段用 VLA，下一段用原语”的混合调度器。两条路线可以并行开发，不能让两个运动控制进程同时占用同一手臂。

### 2.2 VLA 不够好时的计划

**先查适配，再决定训练。** 需要检查相机视角、本体状态定义、归一化范围、动作坐标、单位、旋转表示、夹爪语义、控制频率与动作块执行方式。没有完成这些核验，不能把失败全部归因于模型能力。

| 分支 | 要做的事 | 主要困难 | 推进条件 |
| --- | --- | --- | --- |
| 直接部署公开策略 | 用明确指令和可重复场景检查接近、闭爪、抬升 | 跨机器人、跨场景差异 | 实际动作符合目标且能形成有效接触 |
| 真机数据微调 | 同步采集图像、关节/末端/夹爪状态、实际动作、指令、时间戳和结果 | 示教难、质量要求高、时序和动作语义容易错 | 少量示教能正确回放，再扩大采集；权重和统计能重新部署 |
| 仿真生成数据微调 | 建机器人、夹爪、相机和任务，生成成功轨迹并训练 | 仿真接触和视觉向真机迁移不确定 | 先验证一个真实局部技能，再扩大仿真任务 |
| 动作原语 | 显式编码抓取、搬运、放置和恢复 | 依赖几何和场景约束 | 当前已进入并行实现与真机联调 |

真机微调和仿真微调都尚未完成。它们也不能只带回模型权重：预处理、归一化资产、输入字段和动作定义必须一起版本化。

### 2.3 VLM 不够好时的计划

先改 Harness：使用最新图像、明确左右语义、保留执行摘要、用夹持反馈约束完成判断、允许机械臂让开视野、抓空后重新定位。不能把每一个 blocked 都当成场景确实无法操作。

若仍不足，可以分别尝试更强的本地 VLM、实验室服务器上的 VLM、旗舰多模态 API。API 路线需要实际测量图像传输到可执行决定的总延迟及失败率；目前没有完成 Astra 等外部 API 的接入与延迟验收。

后续也可用公开数据或仿真数据微调 VLM，重点监督目标指代、任务拆解、失败解释和完成判断。VLM 的训练目标是“下一步做什么”，VLA 是“怎样运动”，两者不能混成一套不区分语义的数据。

### 2.4 计算资源路线

| 方案 | 布置 | 当前判断 |
| --- | --- | --- |
| 首选全端侧 | 板内 VLM 和 VLA 常驻，按任务交替推理 | 已有同卡运行记录，可继续推进 |
| 只运行原语路线 | 板内 VLM，控制主机执行原语 | 不需要启动 π0.5，资源最简单 |
| 局域网规划 | 板内 VLA，服务器 VLM | 模型能力或板内延迟不足时的备选 |
| API 规划 | 板内 VLA，远程 API 做高层 | 需实测网络和服务延迟，尚未实现 |
| 轻量模型组合 | 早期 3B VLM 与 OpenVLA | 保留排故与候选价值，不是当前主路线 |

## 4 模型与板端环境

现场识别到的 GPU 是 MR-V100X，显存 32768 MiB；主存约 15 GiB，COREX 4.4。显存和主存是两种约束，不能因为显存有 32 GB 就忽略权重加载时的主存峰值。

当前较强 VLM 使用 Qwen3.5-9B-AWQ，已有容器名 `cix-harness-qwen35-awq`，兼容服务端口 9110，模型 ID `qwen35-9b`。历史部署使用半精度计算、量化权重和受限上下文，具体启动参数以 `deploy/vendor-vlm.sh` 与现有容器为准。

π0.5 使用 `lerobot/pi05-libero`，固定检查点 `9ba5431256f4136a01c224ab0307b0d3035cc92c`，LeRobot v0.4.4 固定源码，并配套兼容 Transformers。`pi05.py` 调用真实模型和前后处理器，不是占位接口。

历史记录中两模型共用 GPU 时约占 23448 MiB，π0.5 热机单次推理曾约 1 秒。这证明该组合能够装载与运行，不能据此保证更大模型也装得下，也不是所有场景的固定延迟。

最近一次原语抓取时恢复了 Qwen 服务，π0.5 没有因原语任务而被要求启动。当前实时状态需查询服务；“曾部署成功”不等于“现在正在运行”。

现场使用 containerd/nerdctl 和 host 网络。手册中的 Docker 镜像是可复用的厂商运行环境，但具体板端工具是 `nerdctl`。优先复用匹配 ARM64、COREX 和设备驱动的环境；不要随便用通用 CUDA 镜像替换底层 torch。

厂商镜像、模型权重、模型服务和机器人适配是四层不同的东西。下载镜像不会自动获得适合 Baxter 的策略，也不一定包含所有权重；下载更强模型还要核对后端算子、视觉输入、显存和接口。

## 5 端到端架构

两条路线都形成“观测—决策—执行—新观测”的闭环。高层 VLM 不直接写电机角度，控制主机也不会在每个关节控制周期等待模型。

```text
中文任务
  ↓
板端任务循环 ← D455 新图、夹爪状态、执行摘要
  ↓ 本地 Qwen VLM
  ├─ VLA 路线：英文子任务 → π0.5 → 动作坐标适配
  └─ 原语路线：技能 + 图像点 → 深度反投影 → base/TCP 目标
                                      ↓
                  Baxter 控制主机：整段预检、连续 IK、轨迹
                                      ↓
                            机械臂和夹爪执行
                                      ↓
                         实测结果、日志、新图回到高层
```

服务默认绑定回环地址。板子通过 SSH 将本地 9102 转发到控制主机的 9102。VLM 使用 9110，VLA 使用 9101。不要把 Windows 上的 localhost 与板子或控制主机的 localhost 混淆。

## 7 开源复用与我们的改写

### 7.1 RPent

直接复用的是 RPent 固定版本的 RPC 客户端基础，以及改编后的 HTTP RPC、有界 VLA 执行循环。对应关系在 `third_party/README.md` 中。

默认任务入口目前是我们自己的 `cix_harness`，不是完整 RPent 原生运行时。仓库已有 `integrations/rpent/robots/baxter/` 和 `check_preview.py`，但不能因此宣称完整上游主运行时、工具调用、任务记忆和真实 Baxter 操作都已经验收。

若后续完善 RPent，应让它连接现有模型和控制服务，而不是将 ROS、完整模型依赖和上游 agent 环境混装。reset 也不能直接解释成机械臂回零；会话重置与真实运动必须分开。

### 7.2 HarnessVLA

HarnessVLA 在本项目中属于架构参考，没有直接复制完整 HarnessVLA 工程。仓库记录的参考思想包括高层 agent、冻结 VLA 局部接触技能、解析原语、任务与全局记忆。

我们的当前实现与完整参考架构的差异是：两条执行路线分开运行；原语恢复主要是明确规则和有限次数；日志不是可以自动检索并复用的经验记忆；还没有技能级混合调度与完整全局记忆。

因此，对外介绍应说“参考相关 Harness 思路，复用 RPent 的部分基础设施并完成 Baxter 适配”，不要说“已完整复现 HarnessVLA”或“已使用完整 RPent 主运行时”。

### 7.3 旧毕设 Baxter-claw

参考仓库：<https://github.com/SkyGit111/Baxter-claw>。固定提交为 `cf923aea646d483b8dbe162eda4855ad560f9797`。

主要参考相机驱动、抓放阶段顺序和 Baxter SDK 调用语义。没有照搬旧项目的固定桌面高度、连接时自动校准夹爪、双臂交接模块。新项目把原语拆成可检查的计划、全路径 IK 和阶段执行回执。

主要 SDK 接口包括 `endpoint_pose`、`joint_angles`、`set_joint_positions`、`Gripper.command_position`、`gripping`、`position`。它们的调用顺序可复用，真实工具尺寸与相机外参不能从旧项目无条件继承。

## 8 原语执行细节

### 8.1 三个坐标概念

相机光学坐标、Baxter base 坐标和 TCP 是不同概念。TCP 是实际夹持参考点，SDK 末端点不一定在长夹指尖端。

图像点先结合对齐深度和相机内参反投影，再经相机到 base 的旋转和平移得到目标。随后由工具姿态和工具到 TCP 的偏移换算 SDK 末端目标：

```text
目标 base 点 = R_camera_to_base × 相机点 + t_camera_to_base
TCP = SDK 末端位置 + R_tool × tcp_offset_tool
```

目标深度使用局部小区域统计；深度空洞、有效点不足或明显跨越边缘时要求重新选点。这样可以避免把背景深度当作方块顶面。

### 8.2 技能

| 技能 | 实际动作 |
| --- | --- |
| pick | 抬高、调整姿态、移到目标上方、开爪、下探、闭爪、验证夹持、抬升、再验证 |
| place / stack | 持物抬高、搬运、下探到支撑高度、释放并验证、撤离 |
| move_to | 经通行高度移动到 TCP 目标，不自动开闭 |
| lift / retreat | 保持姿态沿 base Z 抬升配置距离 |
| open / close | 单独夹爪动作；持物时禁止单独 open，要求通过 place/stack 释放 |
| home | 空载经高处通道到配置待机位置，不是系统回零 |
| clear_view | 抬到通行高度，侧向移到配置观察位，保持姿态与夹持，再重新取图 |

pick 的目标点是物体顶面，按 `grasp_inset_m` 向下进入夹持区域。place 的目标是支撑面，stack 的目标是接收方块顶面；放置高度包含物体底部相对 TCP 的偏移和释放余量。

当前固定几何参数适合限定尺寸的演示物体，不能直接宣称适配任意物体。另一个边界是完整三维避障尚未实现：IK 可达不等于全机械臂与环境均无碰撞。

### 8.3 观测与执行契约

`primitive.observe` 获取新图与状态，并使旧准备计划失效。`primitive.prepare` 消费该观测，完成所有阶段的 IK 预检，只生成一次性计划，不发电机命令。`primitive.execute` 消费计划并执行，记录每一阶段的实测结果。

执行前还检查观测/计划时效、手臂是否被移动、运动预算、标定配置与运行模式。预检失败不执行可行的前半段。通信超时后也不能重新发送同一个 execute，因为对方可能已经运动。

到位误差用于决定是否允许继续接触或释放，现有原语位置判据为 1 cm，不要求 2–3 mm。它是流程阈值，不是全工作区精度承诺。阶段预算和有效期也不是对所有动作统一施加很小位移限制；长动作由阶段轨迹和 `max_leg_m` 等配置管理。

### 8.4 最新恢复逻辑

VLM 返回结构化阻塞原因。遮挡可以触发 clear_view；目标身份不明确、找不到物体等不会被字符串匹配误判成需要移动。

观察位可配置 1–4 个。一个位置无效可尝试下一个，同一恢复阶段不重复回到同一位置；接触抓空后则允许返回此前有效的观察位。让位后必须重新拍照和定位，不能继续使用旧图中的目标像素。

确认抓空且停止处理正常时，返回 `empty_grasp`。新观测仍为空载才自动撤离，然后重新定位；默认最多重试一次。执行中丢物、到位失败、停止失败与不明执行结果不进入普通抓空重试。

深度错误、过期观测和普通目标路径不可达可有限重规划；模型与遥测不一致仍是硬错误。默认总恢复预算 3，技能轮数默认 8，另受控制桥的实际阶段预算约束。完整执行回执保存在日志，VLM 仅接收最近三条简短摘要。

## 10 真机经历与已知问题

### 10.1 为什么不能简单翻转 VLA 坐标轴

此前用户观察左臂持续向错误方向走。离线核对发现，实际电机运动与下发命令方向一致：某段请求约 +Y 8.83 cm，实际约 +Y 8.27 cm。因此没有证据说明控制器把符号执行反了。

更主要的问题是策略输入适配：当前虚拟本体映射属于试配，状态部分维度超出检查点统计范围，可能导致离散化输入饱和。LIBERO 检查点与 Baxter 的视角、夹爪、末端范围和状态语义也存在差异。直接翻转 Y 轴会掩盖问题，不能当作修复。

### 10.2 小幅动作和长轨迹

曾有动作实际只移动约 3.85 mm、距目标仍约 8.97 mm，落在当时 1 cm 容差内。这个结果不足以证明毫米级精度，也不应被当作有效抓取演示。后续增加了连续轨迹和动作段执行，减少频繁停走。

曾有工具倾斜限制提前停止执行。工具轴向约束原本用于贴桌保护，但实际长夹指模型不完整，不能仅用假设几何施加过苛刻限制。现在 VLA 接触约束与原语几何配置分开管理，具体生效配置要看当前运行 scope。

用户也指出机械臂无法在任意初始构型下沿竖直方向走很长距离。更合理的是选择可达中间位置、先抬高再侧向搬运，并检查整段路径，而不是一味加大竖直位移。

### 10.3 标定问题是当前真机关键项

用户给出的桌面上表面约为 base z=-0.18 m，粗估可能在 -0.16 到 -0.20 m。实际安装长夹指不完全包含在模型里，必须区分指尖与 SDK 末端高度。

旧 4 月 20 日相机外参在最近核验中将桌面映射为约 z=-0.047 m，与现场认知相差约 13 cm。这远大于“只有轻微位移”的初始估计，不能直接作为精确下探依据。

最近成功抓取使用人工将左夹指对准画面右侧青色方块建立局部参考，再结合当前桌面法向、旧偏航参考和此前指尖贴桌记录形成局部配置。TCP 轴向偏移是估计，XY 偏移仍有假设。这份配置只覆盖目标附近小工作区，不是完整手眼与工具标定。

要扩大任务空间，应重新测量并在多个点验证相机到 base 的变换及工具偏移。新 clear_view 功能不能修复错误外参，也不能自行把局部标定升级为全桌面标定。

### 10.4 最近一次真实成功

机器人自身左夹爪抓起了画面右侧青色小方块。执行了整段 IK 预检、接近、下探、闭爪、验证和抬升，动作约 14.6 秒。最终夹持反馈 true，开度约 18.3%，图像可见物体在指尖；稳定末端相对闭爪位置升高约 12.9 cm。

当时 VLM 因机械臂遮挡未成功自动定位，目标来自人工局部参考。因此应记录为“人工定位后的原语局部抓取成功”。测试结束恢复只读并保持夹持，未自动释放。不要未经现场查询就假定机器人此刻仍保持同一姿态。

### 10.5 其他已处理的现场问题

机器人与主机时钟曾相差约 0.13 秒，新消息因此被误判为未来消息。新增 `robot_clock_offset_s`，定义为机器人时钟减主机时钟；需实测，不能靠随意加大容差接受陈旧遥测。

D455 曾遇到 USB 接触和进程占用问题。桥在启动时等待真实首帧，退出时关闭设备；切换桥必须等待旧进程释放相机，不能同时启动多个实例。

控制主机还存在旧 Python 2 URDF 解析器与 Noetic Python 3 环境混用问题。项目优先使用 Noetic 的解析器，并保留 KDL 模型与实测末端一致性检查。

## 11 接手后的现场操作流程

### 11.1 先核对版本与设备

现场工程目录历史上分别是：

```text
板子       /home/cix/cix-harness-lab-20261106
控制主机   /home/cothink/cix-harness-lab-20261106
```

先 SSH 登录，确认目录、源码版本、现有进程、模型端口和机器人状态。现场目录可能是文件部署而不是 Git checkout，不能假设一定能运行 git pull。更新源码时保留 `models/`、`vendor/`、本地配置和 `runs/`，先备份，再确认两端代码一致。

`5ce8423` 新增了决策字段与恢复回执，两端应一起升级；不要只换 runner 而保留旧桥。已运行的 Python 进程不会因为磁盘文件改变就自动完整升级。

### 11.2 恢复基础服务

控制主机先设置 ROS 环境：

```bash
source /opt/ros/noetic/setup.bash
source /home/cothink/catkin_ws/devel/setup.bash
export ROS_MASTER_URI=http://192.168.1.100:11311
export ROS_IP=192.168.1.101
unset ROS_HOSTNAME
```

确认没有重复桥后，使用实际本地配置启动只读原语桥：

```bash
cd /home/cothink/cix-harness-lab-20261106
python3 -m cix_harness.baxter --config config/baxter-primitives.local.json
```

板子恢复已有 VLM 容器并等待模型服务就绪：

```bash
cd /home/cix/cix-harness-lab-20261106
sudo nerdctl start cix-harness-qwen35-awq
curl -fsS http://127.0.0.1:9110/v1/models
```

容器已运行时无需重复启动。只有已有容器缺失、确认所需镜像和权重齐备时才走重建流程。专用 SSH 隧道在单独终端或既有后台管理方式下运行：

```bash
bash deploy/robot-tunnel.sh
```

隧道需要板端已配置的密钥和 known_hosts。端口占用时先检查原实例，不能启动多个相同转发。

### 11.3 只读验证与观察位记录

```bash
python3 -m cix_harness.primitive_runner \
  --task '抓起青色小方块' --task-kind pick
```

不带 `--execute` 时只生成计划，不移动。仍需检查目标像素、深度、base 点和整段 IK 是否合理；只读通过不能证明标定正确。

最新观察位记录工具：

```bash
python3 -m cix_harness.record_view \
  --config config/baxter-primitives.local.json
```

前提是人工已将正确的手臂摆到经确认能露出目标区域的位置。工具只读取状态并保存 TCP，不发运动命令；观察位必须在工作区内且不低于通行高度。若在板端记录，需把更新的本地配置放回控制主机，下一次正常启动桥时加载。

不要给两端各自维护一份互不一致的真实几何配置，也不要为了通过校验而直接扩大工作区。

### 11.4 进入真实任务

实际几何、夹爪状态、轨迹空间和现场人员条件确认后，使用已核验配置开启运动：顶层 `commissioned` 与原语 `calibrated` 必须有效，桥启动加 `--arm-motion`，任务入口另加 `--execute`。设置标志本身不是完成标定。

```bash
python3 -m cix_harness.primitive_runner \
  --task '抓起青色小方块并保持夹持' --task-kind pick \
  --max-turns 8 --max-recoveries 3 --max-grasp-retries 1 --execute
```

这条命令会真正动作。应在同一现场会话中先核对物体和夹爪，不能照抄旧测试脚本重放上一次动作。成功后先检查 held 状态，再安排指定支撑面上的放置。不要将独立 open 当作运输结束。

### 11.5 切换到 VLA 路线

原语路线无需 π0.5。要测试 VLA 时再恢复服务：

```bash
sudo bash deploy/pi05-container.sh start
python3 -m cix_harness check-vla
```

控制桥需要切到相应 VLA 配置，不能混用原语 scope。先进行录制图像重推理、坐标审计和只读 IK，再决定真实执行。当前适配问题未解决，不把旧 VLA 命令当作已验证自主抓取方案。

## 12 日志、文件与故障定位

`runs/<时间与ID>/` 保存图像、决策和 `events.jsonl`。控制桥另外记录阶段执行结果。应按同一次任务关联：任务文本、模型版本、配置版本、图像、目标点、预检、发出的动作、实测结果、退出原因。

最近现场证据保存在本地 `examples/lab-20261110/`，控制主机还有 `runs/site-20261110/`。照片、真实外参、遥测和本地配置不进入公开 Git 仓库，公开克隆中没有这些文件属于正常现象。测试使用合成图像，不依赖实验室照片。

| 现象 | 优先检查 |
| --- | --- |
| 无法 SSH | 地址、同一局域网、主机密钥、账号、认证；不要先改机器人代码 |
| 9102 不通 | 控制桥是否存在、SSH 隧道是否存在、回环端口所在机器 |
| 9110 有端口但推理失败 | 模型是否真正就绪、模型 ID、上下文长度、结构化输出 |
| 图像缺失 | D455 USB、独占进程、首帧、相机退出清理 |
| 遥测过期或未来时间 | ROS master、主机/机器人时钟、重复时间戳、实际 offset |
| 三维目标明显不在桌面 | 深度是否落在物体、外参、单位、TCP 偏移 |
| clear_view 没有执行 | 观察位是否配置、是否已在该位置、是否已尝试、工作区/预算/IK |
| IK 无解 | 当前构型、目标高度、工具朝向、连续路径；模型不一致须独立排查 |
| 闭爪不算抓到 | gripping 与开度、物体实际在指间的位置；不能只看 close 返回 |
| 动作响应丢失 | 先读真实状态和日志，不能重发同一 execute |
| 策略方向错误 | 对比策略原始输出、适配后指令和实际位移，分层定位 |

退出码 0 可能代表只读预览完成，也可能是任务验证完成；必须结合运行模式与日志解读。2 表示受阻或预算结束，1 通常是服务/数据/执行错误。不能只凭一个 0 认定真机成功。

## 13 下一步工作优先级

### 第一阶段 完成原语视觉抓取闭环

1. 两端升级到同一恢复版本，确认只读运行。
2. 完成或重新核验相机外参、TCP 和多个桌面点；决定当前局部配置能支持多大范围。
3. 记录有效观察位并预检全路径，现场验证“遮挡—让位—新图定位”。
4. 从固定大小、容易区分的方块开始，完成没有人工指定 base 目标的视觉抓取。
5. 单独验证放置，再验证指定方块堆叠。每一步都保存图像与夹持结果。
6. 在可控条件下验证抓空恢复；不以软件测试代替物理闭环。

### 第二阶段 增强比赛展示效果

在单次成功基础上更换摆位、颜色和指令，检查完成判断、任务记忆需求、长轨迹耗时和恢复效果。先做少量有代表性的场景并针对失败修工程，不安排形式化论文消融。

可以考虑让系统显示当前目标、技能、失败原因和执行结果，帮助现场观众理解；这是后续产品化方向，不是已实现界面。

### 第三阶段 并行推进 VLA

逐字段审计检查点输入和 Baxter 映射，避免状态超范围与错误归一化。用相同录制观测检查原始输出与适配结果，再选择真正匹配的检查点或数据微调路径。π0.5 能加载的事实已经成立，下一步重点不是反复证明服务能启动。

### 第四阶段 根据瓶颈升级 Harness 和模型

若原语和 VLA 均有可靠局部技能，再实现统一技能调度；若相同错误反复出现，再做可检索的任务经验；若 VLM 成为主要瓶颈，再测服务器/API 或微调。完整 RPent 主运行时是否值得接入，应以减少维护和改善任务效果为依据，而不是为了更换框架名称。

## 14 接手同学的开发约定

代码修改继续在 `baxter_harness` 仓库进行。不要把旧毕设仓库重新当作主工程，也不要把 `.local/` 中带有一次性动作的操作脚本当作公共入口。

修改执行语义后运行：

```bash
python3 -m unittest discover -s tests -v
python3 -m compileall -q cix_harness deploy integrations
```

对低风险文字修改不必增加机械重复的测试。对运动回执、恢复状态机、坐标变换和预算逻辑，应验证有意义的失败分支，尤其是“可能已经执行但响应丢失”。

每次现场记录清楚是哪一版源码、哪一份配置、哪一个模型、哪条路线、哪个手臂。失败记录同样有价值，但只记录实测结论；人工摆位、人工定位和模型自主定位须明确区分。

阅读历史 README 时注意日期：早期内容仍有“π0.5 待部署”“原语仅备选”“3B 主路线”等当时状态。当前决策以本交接和 README 最新章节为准，旧命令只用于理解历史，不直接作为当前操作入口。
